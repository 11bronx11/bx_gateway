# 单机小型服务 API 网关对比测试设计书

状态：待评审

目标平台：Linux 单机

主测对象：Bronx、Spring Cloud Gateway、Kong Gateway

非主测对象：Nginx（仅作直连/裸转发校准，不参与 API 网关价值结论）

## 1. 测试目的

本测试不证明 Bronx 是通用场景下最快、功能最多或生态最完整的网关。它要验证一个有明确
适用边界的工程结论：

> 在单机、小型服务、CPU 和内存有限、不需要跨机配置中心的场景中，Bronx 能否用较小的
> 总资源和部署代价，稳定完成一条包含协议校验、安全治理、路由、观测和转发的完整 API
> 请求链，并提供足够的业务容量和可操作的故障定位能力。

测试只设两条核心比较线：

1. **Bronx vs Spring Cloud Gateway：完整 API 请求链性能对比**。回答固定资源下的吞吐、
   延迟、CPU、内存和安全短路效率，不扩大为全产品能力排名。
2. **Bronx vs Kong Gateway：目标场景适用性对比**。在单机、小型服务、有限资源前提下，
   比较覆盖、观察、稳定、部署和总资源代价，性能只判断是否满足目标负载，不追求极限竞速。

正式证据以同一组 `G-FULL-1000` 综合主测试为核心：每个产品在完整治理能力始终开启时，
一边接受合法请求、安全拒绝请求、WebSocket 和变更/故障事件，一边采集性能、资源、日志、
指标和恢复结果。功能、性能和资源不拆成三套互不相干的主测试。

两条主线共同回答五个问题：

1. **性能**：完整 API 请求链开启后，在固定资源预算内能稳定处理多少请求，延迟和 CPU
   成本是多少。
2. **覆盖**：鉴权、WAF、IP 封禁、路由、限流、WebSocket、热更新和上游治理是否真的
   生效，拒绝请求是否在到达上游前终止。
3. **观察**：出现 401、403、429、502、503、504、慢请求和配置错误时，是否能通过管理面、
   指标、日志和请求 ID 定位责任层。
4. **稳定**：持续混合流量、配置热更新、规则变化、上游故障和控制面重启期间，是否崩溃、
   泄漏、错误放行或静默失去治理能力。
5. **总成本**：达到同等能力需要多少常驻进程、CPU、PSS/RSS、线程、FD、磁盘、配置、
   外部服务和运维步骤。

## 2. 结论边界

### 2.1 允许得出的结论

- 在本报告记录的机器、版本、配置、资源限制和负载下，哪套方案满足预先冻结的“小型服务”
  目标。
- 在等价能力链下，各方案的吞吐、延迟、CPU、内存和运行组件差异。
- 某项能力是内建、依赖官方插件、依赖外部服务、需要自定义代码，还是无法在本轮实现。
- 在指定故障和变更场景中，系统是否可观察、可恢复、可回滚。

### 2.2 不允许得出的结论

- 不把单机 loopback 结果写成生产容量或跨机网络结论。
- 不把 Bronx 的场景优势写成对 Spring Cloud Gateway 或 Kong Gateway 的全面替代。
- 不比较产品没有共同覆盖的 TLS、HTTP/2/3、服务发现、多租户、开发者门户、跨地域调度、
  插件生态和分布式一致性能力。
- 不用单轮最好成绩、关闭关键功能后的成绩或不同运行载体的成绩证明优劣。
- 不用 Nginx 纯反向代理吞吐评价 Bronx 的 API 网关价值。
- 所有单次负载和稳定性运行最长 5 分钟；5 分钟分阶段结果只证明短时持续负载、变更和
  故障恢复能力，不外推为数小时或长期无泄漏结论。

## 3. 场景定义

### 3.1 目标用户

- 一个团队维护少量 HTTP API 和 WebSocket 服务。
- 单台 Linux 主机部署，无 Kubernetes，无跨机配置中心。
- 上游为少量本机或同内网服务；本测试固定使用 5 个实例以覆盖权重、健康检查和故障隔离。
- 日常流量主要在 100 至 1,000 RPS，允许短时突发至 2,000 RPS。
- 需要入口鉴权、基础攻击拦截、来源封禁、限流、路由、热更新和故障定位。
- 更重视资源可控、行为可理解和部署简单，而不是协议、插件和平台能力的最大集合。

### 3.2 主要资源模型

主结论和扩展验证使用以下三个单核内存档位。限制作用于网关方案的**全部常驻组件**，不只限制
数据面主进程。

| 档位 | 网关方案 CPU | 网关方案内存上限 | 用途 |
|---|---:|---:|---|
| S1 极小单机 | 1 个 CPU | 512 MiB | 主场景和主结论 |
| S2 小型单机 | 1 个 CPU | 1 GiB | 内存余量验证 |
| S3 宽松单机 | 1 个 CPU | 2 GiB | 内存敏感性验证 |
| C1 容量补充 | 2 个 CPU | 2 GiB | 两健康上游完整成功链容量阶梯，不进入 S1 主表 |

当前测试机是 4 核 AArch64，可按下列方式隔离：

- CPU 0-1：负载发生器。
- CPU 2：被测网关方案的全部组件。
- CPU 3：受控上游。
- 使用 cgroup v2 统一限制并统计网关方案的 CPU、内存和进程；`taskset` 只作为额外绑核，
  不能代替总资源 cgroup。

C1 容量补充单独使用 CPU 0 运行负载发生器、CPU 1-2 运行被测网关方案、CPU 3 运行两台受控
上游；三组亲和性不重叠。该拓扑只用于 2 CPU / 2 GiB 容量结果，不与单核 S1-S3 结果混写。

若 512 MiB 下某方案无法启动或稳定运行，记录为“S1 不满足”，随后可在 S2 继续测试，不能
临时只给该方案放宽资源后仍放入 S1 主表。

### 3.3 运行载体

优先使用宿主机原生进程和 loopback 网络。若某个对照方案只能通过容器可靠部署，则参与同一
横向结果的方案都必须使用 host network 容器，并把容器运行时可归属的资源计入说明。
不能混用“Bronx 原生进程、对手 bridge 容器网络”的结果。

## 4. 对照方案

### 4.1 Bronx

完整模式包含：

- `gw`：数据面、管理面、路由、安全中间件、指标、日志、WebSocket 和上游治理。
- `hub`：本机 IP-ban 决策、规则同步和 SQLite 持久化。
- `banctl`：按需执行的管理 CLI，不计为常驻进程，但计入部署产物和运维步骤。
- `bronx.yml`、`gateway.yml`、`hub_bronx.yml`、`hub.yml`。

主性能链必须开启 request-id、真实客户端 IP、安全响应头、结构化访问日志、指标、IP-ban
查询、WAF、路由、JWT 鉴权、路由级限流、连接池和代理。详细 trace 保持关闭，只在诊断
场景按需开启。

### 4.2 Spring Cloud Gateway

使用固定版本的 Spring Cloud Gateway Server WebFlux、Spring Boot、Java 21、Spring
Security OAuth2 Resource Server/Nimbus JWT 和 Actuator/Micrometer。限流使用 SCG 官方
`RequestRateLimiter` 与 Bucket4j/Caffeine 集成，熔断使用 Spring Cloud CircuitBreaker 与
Resilience4j，负载均衡和健康检查使用 Spring Cloud LoadBalancer。动态 IP 策略使用官方
`XForwardedRemoteAddr` 谓词和 Actuator RouteDefinition API。

Spring Security `StrictServerWebExchangeFirewall` 负责请求防火墙，测试规则覆盖本合同的四类
样本；它不是完整 WAF 或 OWASP CRS 实现。因此报告必须写成“官方请求防火墙 + 本轮规则”，
不得把这一项扩大为 Spring 内建完整 WAF。

若某项能力需要 Redis、额外进程或自定义 `GlobalFilter`：

- 必须保存依赖版本和完整源码/配置。
- 额外进程必须进入同一个资源 cgroup 并计入部署复杂度。
- 不得把自定义实现描述为 Spring Cloud Gateway 原生能力。
- 不得为追求性能实现比 Bronx 语义更弱的空过滤器。

### 4.3 Kong Gateway

固定 Kong Gateway 版本、发行版/许可证和镜像或安装包摘要，测试两个明确分开的部署模式：

- `Kong DB-less`：声明式配置保存在内存中，不使用数据库，作为最贴近单机小型服务的主对照。
- `Kong traditional + PostgreSQL`：网关节点连接数据库保存 Route、Service 和插件配置，
  作为动态管理能力及其部署代价的补充对照。

JWT、IP Restriction、Rate Limiting、Prometheus、Correlation ID、WebSocket 和上游健康检查
优先使用该发行版可用的官方插件或官方配置。需要企业许可证、第三方插件或自定义 Lua 的能力
必须单列并计入成本；不能默认企业插件免费可用。无法形成“WAF/限流事件自动上报并转为动态
封禁”的部分必须标记为 `UNSUPPORTED`、`PASS-EXTERNAL` 或 `PASS-CUSTOM`，不得用静态
IP Restriction 冒充完整闭环。

DB-less 与 traditional 的配置更新、可用插件和管理方式不同，两种模式必须分别通过能力合同、
分别采样资源，不能把一个模式的能力和另一个模式的资源拼成一条结果。

### 4.4 Nginx 的位置

Nginx 只承担两个校准任务：

1. 直打受控上游，确认负载发生器和上游没有先成为瓶颈。
2. 可选裸转发路径，估算多一跳 HTTP/1.1 转发的基础成本。

Nginx 不进入“完整 API 网关性能”“功能覆盖”“总资源成本”和最终推荐排序。若为 Nginx
增加 Lua、JWT、限流、动态配置等能力，该方案应按 OpenResty/Kong 类方案重新命名和计量。

## 5. 等价能力合同

每个方案都必须满足同一份能力合同。合同关注外部行为，不要求内部实现相同。计时前只执行
最小启动和测试夹具预检；正式能力结论必须来自综合主测试承载负载时的在线断言，不能用一轮
空载功能演示替代。

| 编号 | 能力 | 必须满足的外部行为 |
|---|---|---|
| C01 | HTTP 校验 | 合法 HTTP/1.1 正常处理；CL/TE 歧义、畸形 framing 不转发上游 |
| C02 | Request ID | 接受或生成请求 ID；响应、访问日志可关联 |
| C03 | 真实客户端 IP | 只信任指定代理；伪造 XFF 不能绕过限流和封禁 |
| C04 | 路由 | 按 host/path/method 命中；支持 prefix strip 和请求头改写 |
| C05 | JWT | 校验签名、过期时间、issuer 和 scope；非法 token 返回 401/403 |
| C06 | WAF | 对统一的 SQLi、XSS、路径穿越和扫描器样本在上游前返回 403 |
| C07 | IP 封禁 | 已封来源在上游前返回 403；解封后恢复；动态更新有可观测结果 |
| C08 | 限流 | 按真实客户端 IP 执行令牌/计数限制；超限返回 429；窗口后恢复 |
| C09 | 观测 | 暴露请求、状态、路由、延迟、上游、拒绝原因等指标和结构化日志 |
| C10 | HTTP 代理 | 保留正确 body/framing，改写逐跳头，复用上游连接 |
| C11 | WebSocket | 先完成鉴权和限流，再完成 101 和双向文本/二进制传输 |
| C12 | 热更新 | 更新路由/上游/策略时不中断进程；错误配置不污染当前可用配置 |
| C13 | 上游治理 | 健康检查、超时、并发保护和故障隔离的配置与状态可见 |

每项结果只能标记为：

- `PASS-INTERNAL`：进程内建能力通过。
- `PASS-PLUGIN`：官方/公开插件通过。
- `PASS-EXTERNAL`：依赖额外常驻服务后通过。
- `PASS-CUSTOM`：依赖本次维护的自定义代码后通过。
- `UNSUPPORTED`：本轮无法达到合同。
- `FAIL`：配置声称支持，但行为断言失败。

存在 `UNSUPPORTED` 或 `FAIL` 时，该方案不能进入“完整等价链”主性能表；可以继续测最接近
配置，但必须放在非等价附表中。

## 6. 统一业务配置

### 6.1 上游和路由

- 两个相同的受控 HTTP upstream，响应固定 256 B JSON，并提供请求计数和故障控制接口。
- 一个受控 WebSocket echo upstream。
- 16 条路由：4 条 exact、12 条 prefix，覆盖 GET/POST、strip prefix 和请求头改写。
- 主压测路由 `/api/items` 使用两个等权 upstream。
- 健康检查开启；连接池和合理的总/connect/read 超时开启。

负载开始前先直打 upstream，实际吞吐至少达到本轮最高目标的 2 倍，且 CPU 不饱和；否则本轮
容量结果无效。

### 6.2 安全和治理

- JWT：HS256，同一密钥、issuer、过期时间和 `read` scope；token 在正式轮次前生成并保存摘要。
- trusted proxy：只信任负载发生器使用的 loopback/固定地址。
- 限流：主成功路径使用 1,024 个确定性客户端 IP，使每次请求都执行限流检查但不产生 429。
- WAF：开启同一组 URL/query/header 规则；主成功请求为干净输入。
- IP-ban：启用查询和动态更新；主成功请求不在封禁集合中。
- 访问日志：结构化、异步、写本地文件；所有方案使用相同文件系统和轮转条件。
- 指标：始终开启；详细 trace 默认关闭。

### 6.3 主成功请求经过的链路

```text
HTTP framing 校验
  -> request-id / client-ip
  -> 结构化访问日志与指标
  -> IP-ban 查询
  -> WAF 检查
  -> 路由匹配与请求改写
  -> JWT 签名、issuer、过期时间、scope 校验
  -> 路由级限流
  -> upstream 选择、连接池、HTTP 转发
  -> 响应状态与延迟观测
```

WebSocket、非法 JWT、WAF 命中、已封 IP 和超限请求与主成功路径放在同一组综合测试中执行，
但必须使用独立场景标签分别统计状态、延迟、CPU 成本和 upstream 增量，不能只看混合后的
总体平均数。

## 7. 测试项目

### 7.1 P0：环境和证据预检

记录并冻结：

- UTC 时间、Git commit、工作树补丁、二进制/JAR/镜像 SHA-256。
- 内核、CPU 型号/拓扑/频率策略、内存、cgroup、文件系统和限制值。
- 编译器、CMake、JDK/JVM 参数、Spring、Kong、PostgreSQL、Vegeta/k6 版本。
- 所有渲染后配置、环境变量（密钥只保存不可逆摘要）、端口和启动命令。
- 测试前 5 分钟主机 CPU idle、可用内存和后台高负载进程。

预检失败条件：端口冲突、资源限制未生效、上轮进程残留、上游容量不足、时间同步异常、磁盘
空间不足，或无法确认实际加载的配置。

### 7.2 F：综合主测试中的能力断言

以下断言由综合负载发生器在正式计时期间持续执行，不是独立于性能测试的另一套用例：

1. 正常 JWT 请求为 200，五个 upstream 都可达、都接受健康检查并收到数据流量。
2. 缺 token、坏签名、过期 token、错误 issuer、缺 scope 得到预期 401/403，upstream 增量为 0。
3. WAF 四类样本得到 403，upstream 增量为 0，指标和日志给出拒绝原因。
4. 手工封禁、自动封禁、规则同步、解封恢复都可观察；不支持自动闭环的方案明确标记。
5. 限流产生 429 和恢复，不能因伪造 XFF 更换限流身份。
6. exact/prefix/host/method 路由、strip prefix、header set/remove 行为一致。
7. WebSocket 在合法认证下 echo 成功，非法认证不能建立隧道。
8. 配置更新生效；无效配置被拒绝，旧配置继续服务。
9. 上游 503、断连、超时会产生可区分的状态和指标，恢复后 endpoint 重新接流量。
10. `/metrics`、路由/配置快照、健康状态、结构化日志和 request-id 关联可用。

任一能力断言失败，都保留当时的性能和资源数据用于诊断，但对应运行不能进入“完整能力链”
主对比表。只有响应状态正确还不够，安全拒绝还必须以 upstream 前后计数证明没有穿透。

### 7.3 G：完整综合主测试 `G-FULL-1000`

Bronx、Spring、Kong DB-less、Kong traditional + PostgreSQL 在 S1-S3 各执行一次相同的正式综合测试。
这是能力、性能、资源、观测和短时恢复结论的共同证据源；产品只允许在启动、配置更新和进程
枚举处使用适配器，业务请求、事件顺序和断言代码必须共用。

固定条件：

- 资源档位依次为 S1、S2、S3，即整个网关方案总计 1 CPU 和 512 MiB、1 GiB、2 GiB；
  S1 是主场景，S2/S3 用于内存敏感性验证，三档结果不得混写。
- 计时前完成 60 秒以上预热和最小 smoke，正式计时固定 5 分钟。
- 四个产品配置严格串行运行，同一时刻只允许一个被测方案占用目标 cgroup；执行顺序使用
  固定随机种子生成并写入证据，不能三组并发，也不能长期固定把某个产品放在最后。
- HTTP 使用固定 1,000 RPS 的开环负载连续运行 300 秒，同时维持 100 条已鉴权 WebSocket
  连接。容量爬升只在独立的 2 CPU / 2 GiB P2 测试中执行，不与综合主测试混写。
- 五个 HTTP upstream、一个复用 A 实例的 WebSocket upstream、公共路由和第 6 节完整治理
  配置始终启用。
- HTTP 流量固定为 70% 合法 JWT 完整链、10% 缺失/非法 JWT、5% WAF、5% 已封 IP、
  5% 独立身份限流突发、5% 路由未命中或合法 POST/body。
- 每个请求带场景标签和唯一 request-id；负载发生器不自动重试。
- 认证拒绝桶轮换缺 token、坏签名、过期、错误 issuer 和缺 scope；WAF 桶轮换四类样本；
  路由桶覆盖 exact/prefix/host/method、strip prefix、header 改写、POST/body 和伪造 XFF。
- 另以低频旁路探针覆盖畸形 HTTP framing、非法 WebSocket 握手、健康/配置快照和指标抓取；
  旁路探针不计入 1,000 RPS，但其 CPU、内存和日志成本仍计入整个方案。
- 第 7.9 节的更新、故障、控制面恢复和日志轮转时间表在流量不中断时执行。

同一轮必须同时产出五类结果：

1. **能力**：按场景标签统计期望状态、响应内容、路由结果、WebSocket echo，以及 upstream
   前后计数；映射回 C01-C13。
2. **性能**：合法完整链单独计算 QPS、P50/P90/P95/P99/Max；JWT、WAF、封禁和限流拒绝
   各自计算 QPS、P99 和语义正确率；另报整组实际发送率。混合运行的 CPU 只归于整组，
   不伪造无法从并发流量中分摊出的单路径 CPU。
3. **资源**：每秒汇总方案 cgroup CPU、memory.current/peak、总 PSS/RSS、线程、FD、
   context switch、磁盘写入和日志增长，保留稳态中位数和事件峰值。
4. **观察和恢复**：对每次拒绝、配置更新、upstream 故障和控制面变化保存请求 ID、日志、
   指标前后快照、状态快照、恢复时间和实际流量结果。
5. **稳定**：记录崩溃、OOM、意外重启、错误放行、线程/FD 回落和首尾健康窗口 PSS；结论
   仅限这 5 分钟场景。

主报告禁止给出一个混合 P99 或“所有请求 2xx 成功率”。它必须至少分成合法完整链、安全拒绝、
故障窗口和恢复窗口四类，否则预期的 401/403/429 会污染性能结论，故障期 5xx 也会被错误地
算成产品缺陷或被总体平均数掩盖。

### 7.4 P1：Bronx vs Spring 固定负载补充

本组用于在综合主测试之外补充负载曲线和边界定位，不取代 `G-FULL-1000`。只有 Bronx 和
Spring 进入本表；两者必须使用等价的完整成功链配置，全部治理能力保持开启。

| 档位 | 目标速率 | 持续时间 | 重复 |
|---|---:|---:|---:|
| L1 | 100 RPS | 60 s | 3 |
| L2 | 500 RPS | 60 s | 3 |
| L3 | 1,000 RPS | 60 s | 5 |
| L4 | 2,000 RPS | 60 s | 5 |

每个产品正式测量前至少预热 60 秒；Spring 必须完成 JVM/JIT 预热后再采样。产品执行顺序按轮次
轮换，避免固定把某个产品放在主机最空闲或最繁忙的时段。L3 完成后再保持 1,000 RPS 5 分钟，
观察 JVM 预热后 GC、连接池和 Bronx 资源的短时稳定区间，避免只比较一分钟样本；该阶段不作为
长期稳定性或内存泄漏证据。

主报告记录：

- 目标/实际 QPS、语义成功率、状态码和错误类型。
- P50/P90/P95/P99/Max。
- 网关方案总 CPU、每百万成功请求 CPU 秒。
- cgroup memory.current/peak、总 PSS/RSS、线程、FD、context switch。
- upstream 请求数，证明拒绝或失败没有被“成功率”掩盖。
- 日志写入量、指标抓取成功率和采集开销。

### 7.5 P2：2 CPU / 2 GiB 健康容量阶梯补充

独立入口为 `capacity_2c2g/run.sh`。四个产品均可执行，但 Bronx vs Spring 是性能主线，Kong
结果只作其单机适用性补充。每个产品使用两台等权健康上游，完整成功链、访问日志、指标、
健康检查、熔断和连接池始终开启；限流设为远高于最高档而不是关闭。不开故障注入、动态变更和
高精度 trace，这些证据由 `G-FULL-1000` 提供，不能与容量结果互相替代。

每轮使用开环 500、1,000、2,000、4,000、8,000、16,000、32,000 RPS，每档 8 秒；每个产品
启动并预热一次后顺序执行 3 个独立测量，报告三次平均、最小和最大值。某档首次不满足稳定
条件时停止该轮更高档位，不能用闭环客户端的完成速度反推容量。三轮均通过 32,000 档时只报告
`>=32,000 RPS`，不把测试上限冒充精确容量。

“稳定交付点”要求同一档位 3 轮全部满足：

- 实际发送率不低于目标的 99%。
- 语义成功率不低于 99.9%，且无非预期 5xx。
- 限流 429 为 0，证明高限流阈值没有成为容量瓶颈。
- k6 丢弃迭代比例不超过 1%，客户端 P99 不高于 100 ms。
- 负载发生器和 upstream 未饱和。
- 没有 OOM、进程重启、FD 耗尽或治理能力失效。

失败档结束后，以相同总 RPS 对两台 upstream 并发直连。直连也失败则标记为负载发生器或上游
边界，不能归因给网关；直连通过只排除上游容量不足，仍需结合 k6 drop、CPU 和日志区分网关
数据面与负载发生器。报告同时展示 P99 是否低于 10/50/100 ms，100 ms 是预先冻结的稳定门槛。

### 7.6 P3：Bronx vs Spring 安全短路效率补充

分别使用 100%、50% 混合比例运行以下请求：

- 已封 IP。
- WAF 命中。
- 非法 JWT。
- 限流 429。

记录 Bronx 和 Spring 的拒绝 QPS、P99、CPU/请求、upstream 增量和拒绝原因指标。该组验证
“安全策略前置能保护上游”，不与成功转发吞吐混成一个数字。Kong 的相同拒绝路径放入 K 组
场景验证，不参加 Spring 性能主表。

### 7.7 P4：WebSocket 扩展档位

综合主测试已经覆盖 100 条 WebSocket。本组再由 Spring 与 Bronx 比较更高连接档位的建立、
稳态资源和每连接成本；Kong 只做目标档位覆盖与资源验证，并将结果归入 K 组场景报告，不加入
Spring HTTP 容量曲线。

分别维持 100、500、1,000 条连接，每条连接定时发送文本和二进制帧，并执行 ping/pong、正常
close 和上游主动断开。记录：

- 101 成功率、echo 正确率、连接建立 P99。
- 稳态 CPU、总 PSS/RSS、每 1,000 连接增量内存、FD 和线程。
- 鉴权/限流是否发生在 101 前。
- 上游断开后的连接清理时间和指标回落。

### 7.8 O：可观测性与可诊断性

本组主对比为 Bronx 与 Kong。Spring 仍保留功能门禁所需的指标和日志证据，但不进入 Kong
场景适用性排序。事件在综合主测试中统一注入，并要求仅通过公开管理面、指标和日志作答：

| 事件 | 必须能够回答的问题 |
|---|---|
| 无 token | 谁返回了 401，是否到达 upstream |
| WAF 命中 | 哪类规则、哪个客户端、是否触发封禁 |
| 限流 | 哪条路由、哪个 key、何时恢复 |
| upstream 503 | 哪个 endpoint 返回，熔断状态如何变化 |
| connect/read timeout | 失败发生在哪一阶段，最终为何是 502/504 |
| 慢请求 | 总延迟、upstream 延迟和网关处理能否区分 |
| 配置错误 | 新配置为何失败，当前生效版本是否保持 |
| 控制面断开 | 规则版本、连接状态、同步滞后和恢复是否可见 |

每个事件保存：触发命令、请求 ID、相关日志、指标前后快照、路由/状态快照、定位步骤和结论。
记录能否完成、所需命令数和定位时间，但不把人工速度合成一个主观“易用性总分”。

Prometheus/Grafana/Loki 等存储展示层不计入网关基础资源；需要比较完整观测栈时，所有方案使用
同一套外部采集组件并另列资源。Bronx 动态 trace 的性能开销单独测量，不能让对手常关日志而
Bronx 全量 deep trace。

### 7.9 S：综合主测试的稳定性和变更时间表

四个产品配置都按本时间表完成 `G-FULL-1000`。其中 Bronx 与 Kong 的结果进入单机场景稳定性
对比；Spring 的结果用于完整链性能、能力和资源解释，不加入 Kong 场景适用性排名。所有方案
先在计时外完成预热；本组结论限定为短时持续负载下的变更、故障和恢复，不宣称长期稳定性。

建议流量：

- 70% 合法 JWT HTTP。
- 10% 缺失/非法 JWT。
- 5% WAF 样本。
- 5% 已封 IP。
- 5% 限流突发。
- 5% 路由未命中或合法 POST/body。
- 同时保持 100 条 WebSocket 连接。

5 分钟正式计时使用同一固定事件表：

| 时间 | 流量/事件 | 核心断言 |
|---|---|---|
| 0:00-1:00 | 健康混合流量基线 | 语义正确率、P99、CPU、PSS、线程和 FD 形成首段一分钟基线 |
| 1:00-1:30 | 合法路由/上游热更新并回滚，再提交一次无效配置 | 更新无非预期 5xx；无效配置不污染当前版本 |
| 1:30-2:30 | 单 upstream 依次注入 503、断连、延迟并恢复 | 状态和指标可区分；恢复后 endpoint 重新接流量 |
| 2:30-3:00 | 控制面恢复场景 | Bronx 重启 Hub；Spring 只重启实际依赖的 Redis/外部策略组件，无独立控制面则重载配置源并记为 N/A；Kong traditional 重启 Kong/PostgreSQL；Kong DB-less 重新加载声明式配置并重启 Kong |
| 3:00-4:00 | 混合安全拒绝，并执行手工封禁、自动封禁和解封 | JWT/WAF/封禁/限流原因正确，规则同步可见，安全拒绝不访问 upstream，解封后恢复 |
| 3:15-3:45 | 按需开启高精度诊断后关闭 | Bronx 手动开启限定 path/IP 的 trace；其他方案使用最接近的动态诊断能力；记录定位结果和增量开销 |
| 4:00 | 执行日志轮转并触发重新打开 | 新日志进入新文件，指标和请求处理不中断 |
| 4:00-5:00 | 关闭高精度诊断，恢复健康混合流量并采集最终资源快照 | 服务恢复，状态与流量一致，取得末段一分钟资源窗口 |

5:00 后停止流量，再执行优雅停止并确认连接、UDS、临时文件和子进程回收；停机清理不计入
5 分钟负载时长，但必须记录耗时和结果。正式流量、事件和资源采样使用同一个绝对开始时钟；
资源窗口固定为开始时钟至 5:00，不包含预备等待和 graceful stop。

通过条件：

- 无崩溃、OOM、僵尸进程或意外重启。
- 健康阶段实际发送率不低于目标的 99%，各场景语义正确率不低于 99.9%；预期的
  401/403/404/429 计为正确结果，故障阶段只出现事件定义允许的状态。
- 被安全策略拒绝的请求不访问 upstream。
- 热更新无非预期 5xx；错误配置不改变当前生效行为。
- 故障解除后在预设期限内恢复，指标状态与实际流量一致。
- 线程数无持续增长；FD 回到稳定区间。
- 排除计时前预热后，最后 1 分钟健康窗口的总 PSS 中位数相对最初 1 分钟健康窗口增长不超过
  15%；超过阈值只触发后续泄漏诊断，未超过也不能据此宣称长期无泄漏。

### 7.10 K：Bronx vs Kong 单机场景对比

Kong 对比不以“谁的极限 QPS 更高”为主问题，而以相同小型服务目标是否值得其部署和资源代价
为主问题。主对照为 `Bronx gw + hub` 与 `Kong DB-less`，`Kong traditional + PostgreSQL`
作为动态管理能力补充。

三个配置分别执行：

1. 执行 `G-FULL-1000`，在一轮中形成 C01-C13 能力矩阵、目标负载性能、总资源、诊断事件和
   5 分钟恢复结果。
2. 需要解释边界时再执行 P1-P4 补充测试；补充结果不能替换综合主测试的能力和资源数据。
3. R 组单独记录离线安装、配置、热更新、备份、升级、回滚和清理任务。

Kong 结果必须分别回答：

- DB-less 在不使用数据库时，哪些能力和管理操作受限，换来了多少资源和部署收益。
- traditional + PostgreSQL 增加了哪些本场景实际需要的能力，又增加了多少常驻资源、端口、
  持久状态和故障点。
- WAF 与“风险事件自动转动态封禁”能否使用当前固定发行版直接实现；若需要企业插件、外部
  WAAP 或自定义 Lua，其许可证、进程、配置和维护成本是多少。
- 在 1,000 RPS 目标已经满足时，额外吞吐是否对这个小型服务场景产生实际价值。

### 7.11 R：资源和部署成本

资源测量包含同等能力所需的所有常驻组件。Spring 资源数据服务于性能主线；Kong DB-less 与
Kong traditional + PostgreSQL 的数据服务于单机场景主线：

- 空闲 5 分钟。
- `G-FULL-1000` 全程每秒资源样本、健康窗口 steady 和事件窗口 peak。
- P1-P4 补充测试若执行，复用同一采样器，不另造一套资源口径。
- 启动到 readiness 的时间和启动峰值。

至少记录：cgroup 总 CPU、memory.current/peak、PSS/RSS、进程数、线程、FD、监听端口、磁盘
产物大小、持久状态大小和日志增长。

部署难度通过任务记录，而不是配置行数打分：

1. 在无网络的干净运行目录安装预下载产物。
2. 配置五个 upstream、公共路由和完整治理链。
3. 启动并通过 readiness/能力合同。
4. 新增一条路由并热更新。
5. 提交错误配置并恢复。
6. 查询一次 401、一次 504 的原因。
7. 备份并恢复持久规则。
8. 升级到同系列补丁版本并回滚。
9. 停止并确认资源回收。

每项记录常驻组件、配置文件、命令、权限要求、端口、外部依赖、人工修改点和失败恢复步骤。
源码构建难度与运行部署难度分开报告。

## 8. 数据采集

### 8.1 每秒资源样本

统一采集：

- cgroup：`cpu.stat`、`memory.current`、`memory.peak`、`memory.events`、`pids.current`。
- 进程：PSS/RSS、线程、FD、minor/major faults、voluntary/nonvoluntary context switch。
- 系统：每核利用率、iowait、run queue、可用内存、磁盘写入。
- 网关：健康、请求/状态/延迟、路由、拒绝、upstream、连接池、熔断和控制面状态。
- 上游：收到的请求、连接、错误和故障模式。

不能只比较某个主进程 RSS。JVM、PostgreSQL、Redis、sidecar 或 helper 的资源必须汇总到
方案总值。
Linux 内存主表优先使用 cgroup 总量和进程 PSS，RSS 作为兼容指标保留。

### 8.2 结果统计

- 原始结果逐轮保存，不删除异常轮。
- 整组实际 RPS 按正式窗口中的 HTTP 请求数除以冻结的用例时长计算；k6 因 setup 等待得到的
  原始 rate 只作审计字段，不进入横向主表。
- `G-FULL-1000` 按场景标签和时间阶段分别统计；同时报告整组语义正确率、合法完整链性能、
  安全拒绝结果、故障窗口和恢复窗口，不计算混合 P99。
- `G-FULL-1000` 的 CPU 同时报告总 CPU 秒、每百万语义正确请求 CPU 秒和每百万合法转发 CPU 秒；
  PSS/RSS 报五分钟整体中位数、健康窗口中位数和事件窗口峰值。高精度诊断开启区间只进入
  整体成本和诊断增量，不进入基础稳态性能。
- 五分钟测试只用于识别明显差距。若关键结论依赖小于 10% 的 CPU/PSS 差异或小于 15% 的 P99
  差异，对应两个产品必须反向执行顺序各复测一次；差异方向不一致时报告“本测试无法区分”，
  不能挑选有利轮次。
- 固定负载使用 5 轮中位数；P2 容量边界按其冻结方案使用 3 轮共同稳定上限，同时展示最差一轮。
- P99 使用负载发生器原始样本计算；网关内部桶用于交叉验证，不能替代客户端延迟。
- 同负载横向比较；不同实际 QPS 的延迟不能直接比较。
- CPU 同时报告百分比和“每百万成功请求 CPU 秒”。
- JVM GC 次数/暂停、Kong worker/PostgreSQL 状态、Bronx scheduler/连接状态作为各自诊断项，不混成
  跨产品统一指标。

## 9. 防偏差规则

以下任一情况会使对应横向结果失效：

- Bronx 开启完整链，对手只做裸代理，或反过来。
- 一方关闭访问日志/指标，另一方开启。
- 一方使用宿主机 loopback，另一方使用 Docker bridge。
- Spring 未预热就测量，或只给 JVM 单独放宽内存。
- Kong traditional 只统计 Kong，不统计 PostgreSQL。
- Kong DB-less 与 traditional 的能力取自不同模式，却只采用 DB-less 的资源数字。
- Spring 的 Redis/自定义服务不计入资源和部署步骤。
- 只统计 RSS，忽略共享页、cgroup 总量或子进程。
- 把预期的 401/403/429 当失败，或把安全拒绝和故障窗口混进合法完整链 P99。
- 从混合并发流量中主观分摊某条请求路径的 CPU，而没有独立补充实验。
- 用单轮最好成绩、短于 60 秒的边界样本或事后选择的 QPS 档位下结论。
- 负载发生器或 upstream CPU 饱和，却把平台误判为网关上限。
- 功能断言失败后仍把结果写入“完整链性能”主表。
- 在共享主机突发负载期间把 P99 差值归因于具体实现，却没有直连控制和系统时间线。

## 10. 小型服务适用性判定

Bronx 只有同时满足以下条件，才能支持“适合单机小型服务”的结论：

1. **覆盖成立**：C01-C13 中 Bronx 声称支持的能力全部通过，安全拒绝不触达 upstream。
2. **性能够用**：S1 下 `G-FULL-1000` 的 1,000 RPS 混合业务流量达到发送率和语义正确率
   门槛，合法完整链 P99 明确落入 10/50/100 ms 哪一档，并报告相对 Spring 的总 CPU、PSS；
   若执行 P1/P2，再单列纯合法链 1,000 RPS 和容量边界，不能与综合结果混写。
3. **资源可控**：`gw + hub` 总资源留在 S1 预算内，无 OOM，稳态和峰值均有记录。
4. **观察闭环**：能够从公开指标和日志区分认证、WAF、限流、封禁、网关错误和 upstream
   错误，并通过 request-id 关联请求。
5. **稳定可恢复**：与 Kong 使用同一时间表完成 5 分钟分阶段稳定性测试，覆盖热更新、错误
   配置、上游故障、控制面恢复和日志轮转；结论限定为短时恢复能力。
6. **成本优势有对照**：在等价或明确标注差异的能力下，Bronx 与 Kong DB-less、Kong
   traditional + PostgreSQL 的总进程、总资源、配置和运维步骤有真实差异；不靠删减能力
   获得优势。

不生成综合百分制。最终报告分别给出“覆盖、性能、资源、观察、稳定、部署”六项结论和证据，
避免权重选择掩盖真实取舍。

## 11. 证据目录

实际入口为 `repro/run.sh`。每次调用使用独立目录；产品位于同一轮目录下并严格串行：

```text
repro/results/<UTC>-<suffix>/
  case.json
  manifest.sha256
  metadata.env
  product-order.txt
  source.sha256
  source/
  host/
  products/<product>/
    capabilities.json
    configs/
    events.jsonl
    events/
    logs/
    raw/
    resources.csv
    runtime/
    snapshots/
    summary.json
    status.txt
  report.md
  summary.json
  status.txt
```

必须保存：

- 提交、工作树补丁、依赖锁定文件和所有构建/镜像摘要。
- 渲染后的实际配置，不只保存模板。
- 启停命令、每轮起止时间、退出码和清理结果。
- Vegeta/k6 原始结果或可校验压缩件。
- 每秒资源 CSV、指标前后快照、上游计数和关键日志。
- 配置/产物 SHA-256 清单。
- 失败轮和失败诊断，不能只保留通过轮。

`smoke-20s` 只验证夹具，不得作为性能证据。`full-5m` 对每个产品预热 60 秒、正式执行
300 秒；一次调用是一轮。需要 5 轮中位数时应调用 5 次，让每轮各自拥有目录和 manifest，
不能在同一目录覆盖重跑。

## 12. 执行阶段

### 阶段 A：冻结合同

- 评审本设计书和 1,000 RPS/S1 主门槛。
- 固定产品版本、依赖、配置语义和功能实现方式。
- 明确每项能力属于 internal/plugin/external/custom/unsupported。
- 固定两条报告主线：Spring 性能对比；Kong 单机场景适用性对比。

### 阶段 B：实现隔离测试架构

- 生成独立运行根、端口、日志、SQLite/PostgreSQL 数据和 cgroup。
- 实现受控 HTTP/WS upstream、资源采样和统一清理。
- 先验证直连容量，再接入网关。

### 阶段 C：先完成 Spring 对比

- 配置 Spring 完整能力链，由 Bronx 与 Spring 分别执行 `G-FULL-1000`。
- 从同一轮形成能力、合法链性能、安全拒绝、总资源、观察和恢复证据；需要解释吞吐边界时再
  执行 P1-P4 补充测试。
- 产出独立的 Bronx vs Spring 性能报告，不掺入 Kong 的部署和生态结论。

### 阶段 D：完成 Kong 单机场景对比

- DB-less 与 traditional + PostgreSQL 分开运行、分开计量。
- Bronx、Kong DB-less、Kong traditional + PostgreSQL 分别执行同一 `G-FULL-1000`，再执行
  部署任务；需要解释边界时才运行补充档位。
- 产出独立的 Bronx vs Kong 单机场景报告，不做三方综合性能排名。

### 阶段 E：交叉检查与最终报告

- 检查四个配置的综合用例场景计数、时间阶段、资源口径和能力实现方式是否一致。
- 汇总 Spring 性能结论，以及 Kong 覆盖、观察、稳定、资源和部署结论。
- Nginx 校准结果只放附录，不进入主排名或项目价值结论。

## 13. 最终报告必须回答的问题

1. 在 1 CPU/512 MiB 下，Bronx 和 Spring 的完整 API 请求链能否稳定承载 1,000 RPS？
2. 同样 1,000 RPS 时，Bronx 与 Spring 的 CPU、PSS、P99 和容量边界分别是多少？
3. Bronx 与 Kong DB-less 在目标场景中分别覆盖哪些能力，哪些需要插件、外部服务或自定义
   代码？
4. Kong traditional + PostgreSQL 比 DB-less 增加了什么本场景需要的能力和总成本？
5. 安全拒绝是否真正保护 upstream，代价是多少？
6. 一次 401、403、429、502/504 和慢请求能否被准确定位？
7. 热更新、错误配置、上游故障和控制面重启时是否继续可用并最终恢复？
8. Bronx 与 Kong 的部署、变更、回滚和备份分别需要多少组件与操作？
9. Bronx 的优势来自真实的能力密度和资源差异，还是来自测试配置不等价？
10. 哪些场景应选择 Spring Cloud Gateway/Kong，而不应选择 Bronx？

只有这些问题都有可回溯的原始证据，才能发布“Bronx 为单机小型服务而生”的结论。
